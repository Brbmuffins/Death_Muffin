# Death Muffin server

Backend and operations for Death Muffin. The game is the Godot client (`client/`, with its combat core in `native/`), online only; the Windows launcher is `launcher/windows`. Public site:
https://muffindevelopment.com/death-muffin/ (launcher download, patch notes, leaderboard, benchmarks, play reports).

## Static files (`/var/www/death-muffin/`)

- `site/`: the launcher download page, About, Classes, leaderboard, benchmarks, play reports and patch notes. Copied to `/var/www/death-muffin/` by hand; no script publishes it.
- `client/`: the Godot Windows client and `manifest.json`, written by `publish-godot-client.sh`.
- `play/release-notes.json`, `play/patch-notes.json`: written by `announce-release.sh`; read by the launcher, the site and the client.

### Release flow

1. Merge to `main`. For a release worth naming, add a new top entry (`title`, `items`) to `PATCH_NOTES.json`. Branches that add lines to the same entry merge cleanly: `.gitattributes` routes `PATCH_NOTES.json` through `tools/git/merge-patch-notes.mjs` (register it once per clone with `tools/git/install-merge-drivers.sh`; the VPS clone has it).
2. Backend: `deploy-release.sh <rev> [NNN-name.sql]`. Lobby: `deploy-lobby.sh <rev>` when it changed. Client last: `publish-godot-client.sh <rev>`, which refuses a release while the live lobby differs from the rev's (`LOBBY_SKEW_OK=1` overrides; rollbacks to older revs are exempt). Online play is opened or closed separately with `set-online.sh`.
3. Both scripts end with `announce-release.sh <rev>` (also callable by hand; never fails the caller; `NO_ANNOUNCE=1` skips it in the publish script). It:
   - writes the launcher/site notes: the top `PATCH_NOTES.json` entry if that file changed since the last announced release, otherwise the commit subjects;
   - posts "Death Muffin update is live" in #deathmuffin;
   - marks player bug reports fixed by `Bug report #<id>:` commits as released, with their own notice.
   - **QUIET (backend deploys):** if `PATCH_NOTES.json` did not change, the live notes keep their title and items and no release notice is posted (bug reports are still released).
   - **Rollbacks and repeats** (a rev that is not newer than the last announced one) announce nothing.

The manifest format is in `launcher/windows/README.md`.

## Database and migrations

`backend/migrations/NNN-*.sql` are applied by `migrate.sh` (deploy-release.sh runs it): every file not yet recorded in the `schema_migrations` table
(name, sha256, rev; `055-schema-migrations.sql`) runs once, in name order, and is recorded; a failing file stops the run unrecorded. 001-054 were recorded as a
baseline when the runner came in (2026-10-15). `migrate.sh --pending <dir>` lists what would run. Never edit an applied file (the runner warns on a changed
checksum and does not re-run it); add a new one. Every file must still be additive and idempotent. Numbers are not contiguous (gaps are intentional). Several files are generated from `server/rules/content/` by `tools/build-*-sql.mjs`; those generators have a `--check` mode.
`001-discipline-index.sql` and `003-optional-email.sql` are for fresh installs of the original schema and must not be re-run blindly against the live database.
Real credentials, the initial schema and test accounts are not in Git.

## Shared rules

`server/rules/` (TypeScript) is the server-side source of truth for content and rule tables; `npm run build:server-rules` bundles it into
`backend/gathering/*-rules.cjs` and `server/vps-handoff/necro-progress/necro-rules.cjs`. Never edit those `.cjs` files by hand. See `rules/README.md`. The game's port of the rules is `client/rules/`.
`server/vps-handoff/necro-progress/` holds the necromancer progression routes, store and schema, installed into `backend/necro-progress/` by `deploy-release.sh`.

## Server authority

The client reports level, XP, gold, kills and its bag; the backend decides whether the report is believable. Both switches are read on every request, but the service reads `.env` only at
start, so changing one needs a restart of `death-muffin-auth`.

- **Step 1, plausibility guards** (`backend/authority.cjs`, migration 021): `AUTHORITY_MODE=report` (default) logs what it would refuse and never changes a save; `enforce` clamps what
  is not believable and returns a readable message. Findings are written to `progress_audit` (`[AUTHORITY]` in the log). Accounts in GM mode are exempt (below); a guard that cannot run refuses the write with a 503 (the client retries), never saves unchecked.
- **Step 2, kill ledger** (`backend/kills.cjs`, migration 036): `AUTHORITY_KILLS=off` (default) ignores kill reports, `audit` keeps the ledger and logs differences, `enforce` lets saves claim only what
  the ledger credits (and implies the step-1 clamp). Ceilings come from `server/rules/gameplay/authorityRules.ts`.
- **GM mode** (`backend/gm-mode.cjs`, migration 046, DECISIONS B19): an account with role admin / gm or `gm_enabled` is a normal player until it sends
  `POST /api/gm/mode {on: true}` (in game: Settings -> GM mode); only then is it staff for the guards above. Each switch (`gm_mode`) and each successful write
  in GM mode (`gm_write`) is a `progress_audit` row, and switching on sets `characters.gm_marked` (the leaderboard's GM tag). `GET /api/me` answers `gmActive`.
  GM-mode only: `POST /api/inventory/add-item`, `POST /api/offline/load`, `POST /api/offline/sync-stats`, and a first `POST /api/necro-progress/import`
  carrying a record (a player's starts blank).
- **Progress saves are gains** (`POST /api/character/save-progress {characterId, gains: {xp, gold}, seq, killReports?}`, migration 052, DECISIONS B23):
  the backend adds the gains to its own record (the level is worked out of the XP; stats are its own), runs the guards above on the result
  and answers the character row; a `seq` at or below `character_authority.progress_seq` is a retry and answers `{duplicate: true,
  progressSeq}`. A body without `gains` (totals, clients before B23) is refused with 426 and writes nothing (DECISIONS B32). Gold other routes pay is written by them: gathering,
  labor, contracts (each answers `goldTotal`) and `POST /api/inventory/sell {characterId, items: [{slot_index, quantity}]}` (`sell.cjs`:
  bag slots only, never worn gear, an affixed piece at its affixed price; answers `{sold, gold, goldTotal, bag}`).
- **The bag is the server's** (DECISIONS B25): `POST /api/inventory/sort {characterId, locked?}` -> `{bag, moves}` and
  `POST /api/inventory/use {characterId, uses: [{item_id, slot_index?, quantity}]}` -> `{bag, used}` (`bag-ops.cjs`, rules in
  `vaultRules.ts` sortBag / useItems; only consumables are used up). Every other bag change has its own route. `POST /api/inventory/save`
  (the whole bag) is GM mode only; a player gets a 403 telling them to update.
- **Value ledger** (`backend/value-ledger.cjs`, migration 054, DECISIONS B24): every server write of a character's gold, XP (lifetime total)
  or soul shards adds a `value_ledger` row `{delta, balance, reason, ref}` inside the write's transaction; a failure is logged, never fails the write.
- **Boss kills** in the kill ledger draw first on paid summons (`character_drop_tape.boss_credit` minus `character_kill_ledger.summon_used`,
  migration 053), then on the per-minute allowance. A party session's report is deduplicated by its batch number and neither checks nor
  moves the member's own report `seq`.
- **Server-decided drops** (`backend/drops.cjs`, migrations 047, 049, 050, DECISIONS B20): `POST /api/drops/tape {characterId, next?}` deals each
  drop kind's next seeds (kill 128, elite 48, boss 6, surge 6, floor 8, chest 4; one secret-derived seed per event); `POST /api/drops/claim
  {characterId, kind, n, index, facts, expect?, sessionId?}` rolls that event again from its seed (`gathering/loot-rules.cjs` rollEvent, equal
  to the client's roll by the loot parity fixture) and puts exactly that drop in the bag, once. Bounds: ground open or carried, Wave Speed
  owned, fortune, rising rune chance in roll order, one first kill per boss, a Depths floor within the ledger's proven depth (+1), chests on
  fifth floors, each kind's tape spent no faster than the kill ledger's accepted kills / floors, a surge rate; boss drops are backed by paid
  summons instead (migration 051 `boss_credit`: +1 per summon the character or its party host paid, no rate limit). `DROPS_MODE` (read in
  `drops-mode.cjs`): `enforce` (default) refuses a claim past a bound;
  `audit` logs it (`drop_*` rows in `progress_audit`) and lets them through, rolled with the client's value up to the hard limits.
  A claim refused over budget answers `resync {kind, spent}`: the client rewinds that tape to the server's position (seeds re-used in order).
  `POST /api/loot/roll-gear` (client-named gear) is GM-mode only.
- **A member's build** (`GET /api/sessions/:id/members/:cid/build`, party-sessions.cjs `memberBuild`, DECISIONS B22): the session's host
  reads an active member's level, class, stats, worn slots and progression to build that member's hero. A member's party kills are judged in
  the host's world (the host character's level and Ascension rank).
- **Party sessions** (`backend/party-sessions.cjs`, migration 041, `backend/SESSION-REPORTS.md`): a session host reports what its members killed; each member's part goes through the same kill ledger.
- **Learned runes** (`backend/runes.cjs`, migration 044): `GET /api/runes/:id` lists a character's learned runes; `POST /api/inventory/rune/learn` spends a bag rune and learns it; `POST /api/inventory/rune` puts a learned rune in its rite's socket (or empties it). DECISIONS B17.
- **Friends** (`backend/friends.cjs`, migration 045): `GET /api/friends` (friends with their active character's discipline and level, requests both ways), `POST /api/friends/request {username}`
  (asking someone who asked you accepts), `/accept {accountId}`, `/remove {accountId}` (unfriend, decline or cancel). Mutual, one row per pair, 100 per account, 20 waiting requests; 60 calls a minute.
- **Dropped gear** (`backend/ground.cjs`, migration 043): `POST /api/ground/drop` and `/api/ground/pickup`. Gear dropped from a bag lies on its party session's ground until the session ends; the dropper and members who were in the session when it was found (`loot_instances.found_session_id`, stamped by roll-gear) may take it; the first pickup wins, one transaction each. A bag save may not name a piece on the ground.

```sql
SELECT a.created_at, ac.username, a.character_id, a.kind, a.mode, a.action, a.detail
  FROM progress_audit a JOIN accounts ac ON ac.id = a.account_id ORDER BY a.id DESC LIMIT 50;
```

## Player bug reports

Settings -> Report a bug in the client posts to `POST /api/bug-reports` (10 per account per day; `GET /api/bug-reports/mine` lists the player's own; table `bug_reports`, migration 029).
A release build also files one by itself after a crash (`DmCrashWatch`, DECISIONS B29: message "Automatic crash report ...", `context.crash`).
Each new report gets its own thread in #in-game-reports (message, context, game log attached), opened by the Discord dev agent's runner; the devs bring the agent in with an @-mention (`discord-agent/README.md`). `announce-release.sh` marks reports whose `Bug report #<id>:` fix went live as released.

## Benchmark history

The client uploads every finished in-game benchmark run to `POST /api/benchmarks` (`backend/benchmarks.cjs`, table `benchmark_runs`, migration 048; reply `{ success, data: { id } }`; a repeated `clientRunId` answers the first id; 60 runs per account per day, 30 calls a minute). Everything in it is untrusted and is clamped on the way in; vsync-capped or cancelled runs are stored with `flagged` set and left out of the default list.
Anyone can read: `GET /api/benchmarks` (filters `room`, `discipline`, `size` (`light`, `standard`, `heavy`, `full_party`), `length`, `version`, `gpu`, `account`, `standard=1`, `includeFlagged=1`, `limit`, `before`) and `GET /api/benchmarks/:id` (metrics, breakdown, text report); only admin / gm accounts (GM mode or not) may `DELETE /api/benchmarks/:id`. nginx strips `/death-muffin/api`, so every route is mounted both as `/api/benchmarks` (the game's base) and `/benchmarks` (the site, like `/leaderboard`).
Every run says where it came from: `source` is `player` (the game sent it) or `team` (a team PC's release benchmark uploaded it with its finished `bench` job, below). The server alone sets it (`benchmark_runs.source`, with the PC's id in `source_pc`, migration 058; a POST's own `source` is dropped like any unknown key), and the PC's id is never returned. `saveRun` in `benchmarks.cjs` is the one place a run is stored: the player's POST and a team job's `done` use it, so both get the same validation, the same cap and the same answers for a repeated run.
The public page is `site/benchmarks.html` (`benchmarks.js`): filters (default: every run, flagged ones shown with a badge, team-PC runs with a "Team PC" badge), a per-version trend chart (one line per PC, per PC and setup when several setups are shown; flagged runs left out), the runs table and a two-run compare.

## Play reports

When a play session ends, the game sends one summary to `POST /api/play-reports` (`backend/play-reports.cjs`, table `play_reports`, migration 056; the player's token; reply `{ success, data: { id } }`). Errors are `{ success: false, code, error }`: 400 `bad_request`, 401 `unauthorized`, 429 `rate_limited` (50 reports a day per account, 30 calls a minute), 503 `unavailable` while the table is missing. A report needs a valid `reportId` (16-64 characters, made once per session; a repeated one answers the first id), a `version` and `seconds`; everything else is untrusted and cleaned (unknown keys dropped, strings trimmed and capped, numbers clamped, a bad value becomes its safe default), so a crash found at the next start still counts. The account id (only to count players and cap spam) and the party session ids a report names are never returned.
Anyone can read `GET /api/play-reports/releases` (every release newest first by its first report: `version, reports, players, hours, first, last`) and `GET /api/play-reports/summary?version=<v>` (kept a minute): reports, players, hours, median and average session minutes; by graphics preset and by graphics card (the 15 with most sessions) the sessions, average frame ms (weighted by frames), p99 ms and worst frame ms (the median over sessions of each one's own) and hitches per hour (frames over 50 ms); end reasons and end areas (counts); per area hours, deaths, deaths per hour and average frame ms; and `server`, the server's own numbers. Both are mounted as `/api/play-reports/...` (the game's base) and `/play-reports/...` (the site: nginx strips `/death-muffin/api`).
**The server's numbers** (`server`) cover the party sessions the reports name, each counted once however many of its members reported, and only when an account that named it was a member of it. They are per player-hour, each member counted from joining to leaving (or to the session's end): `kills` and `bosses` are the members' accepted counters in `party_session_members`; `xp` and `gold` are what the members' progress saves paid in that time (`value_ledger`, reason `save`, gains only), because the kill ledger keeps XP and gold only as lifetime totals. `dropsPerHour` is always null: `character_drop_events` carries no party session (a claim's `sessionId` only decides whether a member may carry a drop and is not stored), an event's time is its first pickup (up to 3 minutes after the kill) and drops nobody picks up leave no row, so a time window would count a member's solo Depths drops and miss late pickups.
The public page is `site/play-reports.html` (`play-reports.js`): a release picker (newest first) and the summary as tables.

## Team jobs

The team app (a small Windows app on War's, Muffins' and Helix's PCs; ROADMAP Phase 1, DECISIONS B54 and B55) runs jobs that need a real graphics card; the first kind is `shots`, screenshots of a Discord agent proposal on Low and Ultra (also of a before and an after build), the second `clip`, short videos of a change (one game run per variant to choose from), the third `release`, the release checks of each new client on each team PC (install, quit while loading, screens at four resolutions, stutter, bench, soak; one job, a report in #build-alerts), the fourth `bench`, the benchmark of a release (a `release` job's `bench` step does it now; the job kind stays for the app's older versions and by hand). The server queues a job, one PC claims it, uploads its pictures (or hands over its benchmark runs) and finishes it; the Discord agent's runner (same machine) creates jobs and reads the results. `backend/team-jobs.cjs`, tables `team_members`, `team_tokens`, `team_pcs` and `team_jobs`, migration 057 (`team_jobs.target_pc`: migration 058; `team_jobs.reported_at`: migration 059). Until the migration is applied every team route answers a readable 503 `unavailable`. Errors are `{ success: false, code, error }` with a player-readable `error`: 400 `bad_request`, 401 `bad_login` or `signed_out`, 403 `not_team`, `wrong_pc` or `not_your_job`, 404 `not_found`, 409 `taken`, `not_running`, `too_many` or `not_finished`, 413 `too_large`, 415 `bad_type`, 429 `rate_limited` (120 calls a minute per account, or a bench run past the account's 60 benchmark runs a day) or `too_many_jobs`, 503 `unavailable`, 500 `server_error`.
**Who may use it.** Only accounts in `team_members`, with the team app's own sign-in, never the game's: `POST /api/team/login` `{ username, password, pcId, pcName }` checks the password as `/login` does (the same bcrypt compare and rate limiter, the same words for a refusal), then the account must be on the team (403 `not_team`, asked only after a right password), but it does not claim the account's game session (`session.cjs`), so signing in to the app never ends the player's game and the game's one-session rule never refuses the app. It answers `{ token, expiresAt, accountId, username }`: 32 random bytes as base64url, kept only as its SHA-256 in `team_tokens`, good for 90 days, one live sign-in per PC (signing in again on a PC ends its old one) and at most 5 per account (the oldest ends). Every other app route needs `Authorization: Team <token>`: not revoked, not expired, its account still in `team_members` and active, else 401 `signed_out` ("Signed out: sign in to the team app again."); a game token is refused the same way. The token names its PC, and that is the PC every call acts as: a body, header (`X-Team-Pc`) or query (`?pcId=`) that names another is 403 `wrong_pc`, and one that names none is the token's. `POST /api/team/logout` ends the token it came with. Taking an account out of `team_members` locks its tokens out at once. Rows are added by hand, never by a route or a migration:

```sql
INSERT INTO team_members (account_id) VALUES (1001), (1002), (1003);   -- placeholder ids: SELECT id, username FROM accounts WHERE username IN (...)
DELETE FROM team_members WHERE account_id = 1001;                      -- takes the access away at once, tokens included
```

The runner's routes (`/internal/team/...`, mounted only there) answer 404 to everything except a connection from this machine that carries none of nginx's forwarding headers (`/death-muffin/api/internal/...` would reach them from 127.0.0.1 through nginx, so the headers count) and an `X-Team-Secret` equal to the contents of `TEAM_SECRET_FILE` (default `/home/ubuntu/death-muffin/discord-agent/secret`, the runner's own secret; compared in constant time; a missing or short file refuses everything).
**The app** (each route is also mounted without `/api`, like benchmarks: nginx strips `/death-muffin/api`):

- `POST /api/team/login`, `POST /api/team/logout`: above. `GET /api/team/me` -> `{ accountId, username }`.
- `POST /api/team/heartbeat` `{ pcId, name, version, gpu, mode, state, wait }`: stores the PC (`mode` `ask` | `auto` | `yes`, `state` `gameRunning, fullscreen, onBattery, busy, paused`), renews the heartbeat of the job it runs, sweeps, and answers `{ serverTime, offer, cancel }` (the app sends one right after the last answer, see `wait`). `offer` is the oldest queued job that has not expired, this PC has not said `not_now` to and is not meant for another PC (`id, kind, title, weightS, expiresAt`) or null, by kind first: `shots`, then `clip`, then `release`, then `bench`, then any other kind (`KIND_ORDER`; a release job and a benchmark wait on their PC until it is quiet, so they must never hide a newer screenshots or clip job). Every other team PC is offered a job without a target until one claims it. `cancel` is the list of ids of jobs this PC (this account on this PC) claimed that were cancelled in the last 10 minutes, newest first, at most 20, always present: a cancel reaches a running PC at its next heartbeat, and the app stops the job it runs if its id is named and ignores the others. **`wait`** (optional, 0 to 25 seconds, a number or text of one; default 0, which answers at once as before) makes the heartbeat a long poll: with nothing to say right now (no offer for this PC, and no cancel it has not been told yet: the `cancel` list keeps a cancel for 10 minutes, but one the PC was already answered with is not news) the server holds the request until a job this PC may take is queued (the runner makes one, or a running job goes back to the queue because its PC went quiet), a job this PC runs is cancelled, or `wait` runs out, and then answers exactly as it always did (the offer and the cancels are looked up again at that moment, so a job for another PC, or one this PC declined, ends no wait). The PC is stored at the start of the request, so `last_seen` stays fresh, and the job it runs is kept alive then. In-process, an `EventEmitter` fired by the runner's create (also with `supersede`) and cancel and by the sweep's requeue wakes the held requests; one is opened before the first look, so a job made while it looks is not missed. A PC that hangs up while held is dropped. At most 10 held requests per account: the next is answered at once, as with 0. nginx's 60 s read timeout and Cloudflare's 100 s are above the 25 s. The app (0.3.0) sends `wait` 25 with an HTTP timeout of 40 s and, after each answer, the next heartbeat at once.
- `POST /api/team/jobs/:id/claim` `{ pcId }` -> `{ id, kind, title, payload }`; the claim is one atomic update, so of two PCs one gets it and the other 409 `taken` (also for an expired or cancelled job). The PC that holds it may claim it again. Declining does not forbid a claim. A job made with a target PC (`team_jobs.target_pc`) is offered to and claimed by that PC only: any other PC (or account) gets 403 `not_your_job` ("This job is meant for another team PC.") and the job stays queued.
- `POST /api/team/jobs/:id/decline` `{ pcId, reason }` (`not_now`, `paused`, `busy`): noted in the job's `result.declines` (one entry per PC, its latest answer last, at most 20); the job stays queued for the other PCs; after `not_now` the heartbeat never offers it to this PC again, while `busy` (another job was running) and `paused` only meant not at that moment, so it is offered again.
- `PUT /api/team/jobs/:id/files/:name`: the raw file as the body, at most 40 files a job (pictures, clips, videos and step results together; replacing one is fine; a release job 120, its screens are up to 4 resolutions by 2 UI scales by 6 shots), read with one streaming reader that never takes more than the limit (refused at once when `Content-Length` says more). Two kinds: a **picture**, name `^[a-z0-9_-]{1,60}\.png$`, `Content-Type: image/png`, at most 20 MB (a busy 3840x2160 picture passes 8), which needs the PNG signature, an IHDR first with each side 16 to 4096 pixels, and the closing IEND chunk, for any job but a clip job (a clip job takes no pictures: 400); and a **clip**, name `^[a-z0-9][a-z0-9_-]{0,59}\.mjpeg$`, `Content-Type: video/x-motion-jpeg`, at most 48 MB, only for a `clip` job (400 for any other), which must start with the JPEG marker FFD8 and whose first picture's frame header says each side is 16 to 4096 pixels (a picture claiming more never reaches the decoder). and a step's **result**, name `^[a-z0-9][a-z0-9_-]{0,59}\.json$` (`install.json`, `quit-loading.json`, `screens.json`, `stutter.json`, `bench.json`, `soak.json`), `Content-Type: application/json`, at most 1 MB, valid JSON (any value), only for a `release` job (400 for any other, and a release job takes no clips). A 415 `bad_type` for a wrong type, 413 `too_large` for a body over the limit. Stored as `$TEAM_RESULTS_DIR/<job id>/<name>` (default `/home/ubuntu/death-muffin/team-results`; folders 0750, files 0640, written to a part file and renamed). Answers `{ name, bytes, width, height }` (a clip's size is its first picture's; a JSON file has none). An upload renews the job's heartbeat.
- `POST /api/team/jobs/:id/done` `{ files, log, timings: { downloadS, runS } }`: every named picture must have been uploaded; the result keeps the pictures' sizes, the log (64 KB) and the timings. For a `clip` job `files` names the uploaded `.mjpeg` clips (1 to 40) and the call turns each into `<name>.mp4`, then answers `{ id, status: 'done' }`: `nice -n 10 $FFMPEG -nostdin -hide_banner -loglevel error -y -f mjpeg -framerate 30 -i <clip> -t 10 -vf scale='min(960,iw)':-2 -c:v libx264 -preset veryfast -crf 26 -pix_fmt yuv420p -movflags +faststart -an -f mp4 <part file>` (`FFMPEG`, default `/usr/bin/ffmpeg`; started with an argument array, never a shell, with a bare environment, its working folder and `HOME` the job's folder, `-f mjpeg` so ffmpeg never guesses a format, and killed after 120 s), written to a part file in the job's folder. The video must hold pictures (ffmpeg writes an empty one, and exits 0, when it decoded nothing) and be **under 8 MB** (8,000,000 bytes: Discord's limit for the bot); if it is not, the same clip is made again at `-crf 32`, and a second one that is still not under it fails. A video that is made replaces its clip (the `.mjpeg` is deleted), so the job keeps only the mp4s: `result.files` is `[{ name: 'slow_wraith.mp4', bytes, crf }]` and the runner's `GET /internal/team/jobs/:id` lists them with their paths (it lists the pictures and mp4s, never a raw clip or a part file). A clip that does not become a video (damaged or cut off, ffmpeg gone or past its time, still over 8 MB at crf 32) **fails the job** with the readable reason ("The clip slow_wraith could not be turned into a video (the file may be damaged or cut off).", the time or size words, "The server cannot make videos just now (its video tool is not available)."), with what ffmpeg said added to the stored log and the journal, removes the job's clips and parts, and answers 400 `bad_request` with the same words (a second try would send the same clip). The done keeps the job alive while it works (the heartbeat is renewed before each clip); the transcodes of this machine run one at a time, and a done sent again while the first is still working joins it (one transcode, the same answer). A clip a restart or an earlier try already turned into a video is kept, so a resent done finishes the rest. A clip job that is failed, cancelled or fails its transcode loses its raw clips at once (`team-results` keeps a finished job's folder 14 days).
  For a **`release`** job `done` is `{ steps, files, runs?, log, timings }`: `steps` is 1 to 6 of `{ step, ok, error?, ms? }` (`step` one of `install`, `quit-loading`, `screens`, `stutter`, `bench`, `soak`, each once; `ok` true or false; `error` text of at most 400 characters; `ms` whole milliseconds) and is required, `files` names the pictures and step results it uploaded (each must be on disk, up to 120), and `runs` (optional, needs a `bench` step) are the bench step's benchmark payloads (1 to 6, each at most 64 KB), stored in the benchmark history for the claiming account with source `team` exactly as a `bench` job's are; a run that does not validate or is past the daily cap does not fail the job: the `bench` step is marked `ok: false` with the reason and none of the runs is stored. The job is `done` whatever its steps say (a failed step is a result), the result keeps `steps`, `files` (`{ name, bytes }`), `runs` (`{ clientRunId, id }`), the log and the timings, and a bad body is 400 with the job left running. A release job that stops halfway calls `fail` with `{ error, log, steps }` (the steps it finished; steps that do not read are left out) and the step results it uploaded stay on disk for the report. For a `bench` job the body is `{ runs, log, timings }` instead: `runs` are the benchmark payloads exactly as the game queued them in `pending.json` (what `DmApi.post_benchmark` sends), 1 to 6 of them, each at most 64 KB of JSON. The body may be up to 1 MB (6 runs of 64 KB and a 64 KB log, JSON-escaped, fit): `server.js`'s 512 KB JSON parser skips this route (`readsOwnBody`) and the route reads its own body after the sign-in check, so a bigger one is a readable 413 `too_large` ("That result is too large (the limit is 1 MB)."; refused before it is read when `Content-Length` says so, the job left running) and a body that is not JSON is 400; nginx's team location allows 50 MB. Each is validated by `parseRun` and stored by `saveRun` for the claiming account with `source` `team` and this PC's id, as `POST /api/benchmarks` would (a repeated `clientRunId` answers the first id, so a resent done stores nothing twice); the result keeps `runs: [{ clientRunId, id }]`. A run that does not validate, a list that is missing, empty, longer than 6 or too large, or a run past the account's daily cap **fails the job** with the readable reason (the words of `POST /api/benchmarks`, "Run 2: ..." when there is more than one run, nothing of the job's runs is stored) and the call answers 400 `bad_request` (429 `rate_limited` for the cap) with the same words; a database error leaves the job running for the PC to send again. `POST /api/team/jobs/:id/fail` `{ error, log }` (400 characters). A resent done or fail answers the same success.
- `PUT`, `done` and `fail` are only for the PC that holds a running job (403 `not_your_job` for another account or another PC of the account, 409 `not_running` for a job that is not running, with the reason in the text).

**The runner:** `POST /internal/team/jobs` `{ kind, title, weightS, payload, ttlS, targetPc }` -> `{ id }` (12 lowercase hex; `ttlS` 60 seconds to 7 days, default 1 hour; `targetPc` optional, a PC id: only that PC is offered the job; `supersede: true` (needs `targetPc`) cancels this kind's other QUEUED jobs for that PC once the new one is stored, never a running one, and answers `{ id, superseded: <how many> }`; at most 50 queued or running jobs); `GET /internal/team/jobs/:id` (the row: status, tries, `targetPc`, times as ISO strings (`reportedAt` included), payload, result, error, and `files` with their absolute paths: the pictures of a shots job, the mp4s of a clip job, the pictures and step results of a release job); `GET /internal/team/jobs?kind=&status=&unreported=1&limit=` (the reporter's list: `{ jobs: [row, ...] }`, each row exactly what `GET /internal/team/jobs/:id` returns; `kind` a job kind, `status` `finished` (done or failed), `open` (queued or running) or one status, `unreported=1` only rows with no `reportedAt`, `limit` 1 to 100, default 50; oldest finish first; a bad parameter is 400); `POST /internal/team/jobs/:id/reported` (sets `reportedAt` once for a job that is done, failed, cancelled or expired and answers `{ id, reportedAt }`, the same again; a queued or running job is 409 `not_finished`); `POST /internal/team/jobs/:id/cancel` (queued or running; a finished job is 409); `GET /internal/team/pcs[?days=N]` (PCs seen in the last 2 minutes, or with `days` (1 to 365) in the last N days, with username, mode and state).
**Release checks** (the `release` job; `team-release.sh`, `team-files-prune.sh`, `ops/team-report.sh`; the app's half is `teamapp/`). After every client release the publish runs `team-release.sh <version>`, which reads the live manifest (and checks it is the build asked for), asks `GET /internal/team/pcs?days=14` for the team PCs seen in the last 14 days (none: no job, no files, no build) and hard-links the release's files (`DeathMuffin.exe`, `DeathMuffin.pck`, the combat core's DLL and, when the build has one, `DeathMuffin.assets.pck`) into `/var/www/death-muffin/team-files/release-<24 random hex>/` (a copy where a link is not possible; the app downloads only from `team-files`, and its address check takes any path below it without `..`, `\`, `@`, `#`, `?` or encoded dots and slashes, at most 400 characters). Then it builds the debug export of the same revision, which the screens, stutter and soak steps need (the QA tools start only in a debug build): a scratch worktree of the revision under `~/death-muffin/deploy/`, the revision's own `discord-agent/preview-godot.sh <6 hex> --team` there under `nice -n 10` (at most 25 minutes; a timeout stops the whole process group), the worktree removed again, and the 32-hex folder the script made moved to `release-<hex>/debug/` so it ages out with the release and is never one of the newest 6 previews. If the build fails, times out or the revision's script has no `--team`, the jobs go without those three steps and say why in the publish output. It checks the live manifest still names this build before it queues anything (a publish that went live meanwhile queues its own checks), then queues one job per PC: kind `release`, `targetPc` that PC, title "Release checks of <version>" (the app adds "about N minutes" from the weight), `weightS` 2400 (600 without the debug build), `ttlS` 3 days, `supersede: true` (a PC is only ever offered the newest release's checks), payload `{ version, rev, godotVersion: "4.7.2.stable", builds: [{ label: "release", files: [{ name, url, sha256 (the manifest's), bytes, cacheKey? }] }, { label: "debug", files: [same shape] }], steps: ["install", "quit-loading", "screens", "stutter", "bench", "soak"], setups, screens: { plan: { shots: [...] }, resolutions: ["1920x1080", "2560x1440", "3840x2160", "3440x1440"], preset: "high" }, soak: { minutes: 30 }, args: [] }` (the shape `teamapp/windows/JobPlan.cs` `ParseRelease` reads; the release build is `DeathMuffin.exe`, `DeathMuffin.pck`, the DLL and the art pack, the debug build `DeathMuffinDebug.exe`, `DeathMuffinDebug.pck`, the DLL and the art pack). The standard shot plan is in the format of `client/main/qa_ui_shots.gd` (whole screen, no crop): `bag-tooltip` (the bag with the card of `staff_moon`), `character-sheet`, `spellbook`, `vault` (in the Chapterhouse, the only place it opens), `map` and `hud-fight` (the Hollow Graves, 4 seconds to settle); the plan format holds at most 4 shots a plan (`MAX_SHOTS`), so the game must take 6 for the last two to be pictured. Without the debug build there is no debug entry in `builds`, no `screens` or `soak` settings, and the steps are install, quit-loading and bench. The `bench` step's setups are the Full Party fight in the Hollow Graves with a Gravecaller on Low and on Medium, Full length: `{ preset, room: "graves", class: 2, size: "full_party", length: "full" }` (the budgets' fight, CLAUDE.md; `length` is `quick` or `full`, the benchmark's own words: an unknown one silently becomes Full in the game, so `team-release.test.cjs` holds every setup value to the lists in `client/next/perf/dm_benchmark.gd` and `dm_graphics_preset.gd`). The release exe (`godot-release-<sha16>`), the debug exe (`godot-debug-<sha16>`) and the art pack (`assets-<sha16>`) carry cache keys. The publish no longer queues `bench` jobs: the benchmark is a step of the release job (a `bench` job made by hand still runs). `team-files-prune.sh <root> [keep] [release-days]` holds both clean-up rules, each on its own folder names: the preview builds' 32-hex folders keep the newest 6 (`discord-agent/preview-godot.sh --team` still carries its own copy of that line), and the `release-<24 hex>` folders (and `bench-<24 hex>`, the first hook's name for them) go once older than 4 days, a day past the jobs' 3, so a burst of previews never takes a waiting check's files. The hook is best effort (it prints a line and the publish carries on), runs only for the live folder `/var/www/death-muffin/client` (or with `TEAM_RELEASE=1`; `NO_TEAM_RELEASE=1` skips it) and not for a rollback (a revision that is not newer than the build that was live), and is taken from the published revision itself like `announce-release.sh`. Test overrides: `DM_TEAM_MANIFEST`, `DM_TEAM_ROOT`, `DM_TEAM_URL`, `DM_TEAM_API` (default `http://127.0.0.1:5190`), `DM_TEAM_SECRET_FILE` (the runner's secret), `DM_TEAM_DAYS`, `DM_TEAM_KEEP`, `DM_TEAM_RELEASE_DAYS`, `DM_TEAM_REPO`, `DM_TEAM_WORK`, `DM_TEAM_PREVIEW`, `DM_TEAM_BUILD_TIMEOUT`, `DM_TEAM_NICE`; `team-release.test.cjs` runs it against a fake backend and a stand-in `preview-godot.sh` in a temp repository.
**Pre-release check** (DECISIONS B61; `team-gate.sh`, the `release` job's first two steps). Before the switch to a new build, after its boot smoke, the publish runs the revision's own `team-gate.sh <stage folder> <version> <rev>` (live folder only, `TEAM_GATE=1` forces it, `TEAM_GATE=off` skips it, never for a rollback; at most 11 minutes). It asks `GET /internal/team/pcs` and `GET /internal/team/jobs?status=running&limit=50` for a PC that can take a job soon: seen in the last 90 seconds, not paused, Death Muffin not running, not on battery, and not running a `release` or `bench` job (none: one line says why, and nothing is queued or waited for). It hard-links the stage's `DeathMuffin.exe`, `DeathMuffin.pck`, the DLL and the art pack into `team-files/gate-<24 hex>/` and queues ONE untargeted job: kind `release`, title "Pre-release check of <version>", `weightS` 60, `ttlS` 15 minutes, payload `{ version, rev, godotVersion, builds: [{ label: "release", files }], steps: ["install", "quit-loading"], args: [] }` with the release checks' cache keys. It waits up to 150 seconds for a claim and 420 more for the end (`DM_GATE_CLAIM_S`, `DM_GATE_RUN_S`, `DM_GATE_POLL_S`). Verdict: every step passed: "passed"; a step whose error is the game's own (the app's boot steps begin each such error "The game ": no first screen within 90 s, an exit code, no BOOT OK, no quit within 20 s, a crash report) exits 10 and the publish refuses the build with that line; anything else (no claim, out of time, a download that failed, a job the PC gave up, the gate's own trouble) is "no verdict" or "skipped" and the publish goes on. The job is then cancelled if still open and marked reported (never posted: only live builds are), and the folder removed; `team-files-prune.sh` takes a `gate-` folder a killed gate left after 4 days. `team-gate.test.cjs` runs it against a fake backend, and runs the publish's block with a stand-in gate.
**The report** (`ops/team-report.sh`, timer `death-muffin-team-report` every 2 minutes, `ops/README.md`). It asks the runner's routes for the release jobs that finished and were not reported (`GET /internal/team/jobs?kind=release&status=finished&unreported=1&limit=100`) and for those still queued or running (`status=open`), groups them by `payload.version`, and posts a release once, as one embed in #build-alerts, when every PC's job has finished or 24 hours have passed since the first was queued: a field per PC (name, owner, graphics card; the cards side by side) with a line per step, ✓ or ✗ and the numbers (install: ms to the first screen; quit while loading; screens: how many pictures; stutter: the 3 worst rites with ms, p50/p99 and pipeline compiles, with how many of them ran in the background; bench: average fps per preset and p99; soak: the growth, last 5 minutes against first 5), plus one contact sheet per resolution (rows = PC and UI scale, columns = the shots; Pillow; at most 4 images, each under 5 MB, a PNG or, when too large, a smaller sheet or a JPEG). A PC still working when the 24 hours pass is named as waiting, and its results follow in a "late results" message. Each reported job is then marked with `POST /internal/team/jobs/<id>/reported`; the state file `~/death-muffin/ops/state/team-report.json` remembers what was posted, so a mark that failed is retried and never posts twice. The numbers come from the job's own result files (`<step>.json` and the screens' `<w>x<h>[_s<scale>]_<shot>.png`, read from `<team results>/<job id>/` without following links) and the step list the PC sent with `done` (`result.steps`): the app's own files, `install.json` (`bootMs`), `quit-loading.json` (`seconds`), `screens.json` (`note`), `bench.json` (`summary`: a row per run with `preset`, `avg_fps`, `p99_ms`; `runs` when it fits) and `soak-notes.json` (`notes`: what happened to the PC while the soak ran), and the game's own JSON that the app uploads as it is, read tolerantly because the game's wave-3 flags decide its shape: `stutter.json` `{ rows: [{ discipline, rite, worst_ms, compilations, kinds: { canvas, mesh, surface, draw, specialization } }], p50_ms, p99_ms }` (also read as `rites`, `p50`, `p99`; `kinds.specialization` is the background count) and `soak.json` `{ minutes: [...], growth: { <metric>: <number> } }`; anything else reads as a plain line. A backend without these routes (404) or without the table (503) is quiet. The webhook file is read and never printed. `team-report.sh --dry-run` prints the message and changes nothing; `ops/team-report.test.cjs` runs it against a fake backend and a fake webhook.
**Life of a job:** `queued` -> `running` -> `done` | `failed`; `queued` -> `expired` once `expires_at` passes; `queued` or `running` -> `cancelled`. A running job whose PC sends no heartbeat for 3 minutes goes back to `queued` once (`tries` 1, claim cleared) and fails with "The team PC went quiet" the second time. The sweep runs on every heartbeat and every runner call, so there is no timer; a cancel reaches its PC at the next heartbeat (`cancel`, above), and whatever the PC still uploads, finishes or fails is refused (409 "This job was cancelled."). Every `POST /internal/team/jobs` first removes the result folders (`$TEAM_RESULTS_DIR/<job id>`) of jobs that finished (done, failed, cancelled or expired) more than 14 days ago: only real directories named like a job id whose row says so, never through a symlink, a failure logged and ignored; the job rows stay, and a pruned job reads back with no files.
**Installing it.** Apply migrations 057, 058 and 059 (`deploy-release.sh` does; 058 adds `team_jobs.target_pc` and `benchmark_runs.source` / `source_pc`, and the heartbeat and the benchmark list name them, 059 adds `team_jobs.reported_at`, which the internal job routes name, so they run before the backend restarts; a column that is missing answers a readable 503), then by hand: `mkdir -p -m 0750 /home/ubuntu/death-muffin/team-results`; copy `systemd/death-muffin-auth.service` to `/etc/systemd/system/` (its `ReadWritePaths` lets the service write that folder under `ProtectSystem=strict`) and `sudo systemctl daemon-reload`; add the `/death-muffin/api/team/` location of `nginx-locations.conf` to the live site, with its `client_max_body_size 50m` (nginx's default 1 MB would refuse the pictures, and 9 MB the clips) and its `proxy_read_timeout 300s` (a clip job's `done` waits for its videos), then `sudo nginx -t && sudo systemctl reload nginx`; restart `death-muffin-auth`; for the "Team PC" badge copy `site/benchmarks.html`, `benchmarks.js` and `styles.css` to `/var/www/death-muffin/`. The release checks need no more than that (`/var/www/death-muffin/team-files/` and the runner's secret already exist for the screenshots job) plus the report: `ops/install.sh` installs `team-report.sh` and its timer (`ops/README.md`; it needs Pillow for the contact sheets and the #build-alerts webhook file). The clip job needs `ffmpeg` with libx264 at `/usr/bin/ffmpeg` (the Ubuntu package; set `FFMPEG` in the backend's `.env` for another path) and `/usr/bin/nice`; the unit's `ProtectSystem=strict` leaves `/usr` readable and executable and `ReadWritePaths` the job's folder writable, which is all ffmpeg needs, so the unit file needs no reinstall for clips (its comment line only changed) (`backend/team-jobs.test.cjs` runs the real ffmpeg on a tiny motion-JPEG when this machine has one, and prints a line and skips when it has not). The test backend (`:5194`) mounts the same routes against its own database and answers 503 until that database has the tables.

## Tests

From the repository root: `npm run test:rules` (shared rules), `npm run test:server` (backend, necro-progress and freshness checks of the generated bundles). Lobby: `cd server/death-muffin/lobby && npm install && npm test`.
Backend dependencies: `npm ci` inside `backend/`. The Godot suites are run by `tools/rebuild/run-client-tests.sh`.
